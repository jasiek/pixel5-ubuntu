# Pixel 5 (redfin, SM7250 "lito") boot chain, partitions and downstream kernel

Research date: 2026-11-18. Scope: the boot chain and the Android/vendor side needed to boot a custom kernel, initramfs and an Ubuntu 24.04 rootfs. Mainline status and distro ports are covered by other agents.

Confidence markers: **[V]** means verified from a primary source (AOSP/LineageOS source, Google docs, or a device dump). **[S]** means a single secondary or community source. **[U]** means unverified or inferred, so test it on the device.

---

## TL;DR: how this differs from the Pixel 2 (walleye) recipe

| Topic | Pixel 2 (walleye) | Pixel 5 (redfin) |
|---|---|---|
| Boot image | header v0/v1, Image.gz-dtb (appended DTB) | **header v3** boot.img (kernel and generic ramdisk only) plus **vendor_boot** (vendor ramdisk, **DTB**, vendor cmdline, load addresses) [V] |
| DTB location | appended to the kernel | **vendor_boot DTB section** (base SoC DTBs `lito.dtb`/`lito-v2.dtb`), plus the board overlay from the **dtbo** partition [V] |
| Ramdisk | `skip_initramfs` trick needed | No `skip_initramfs` is expected: the device launched with Android 11 using first-stage init and dynamic partitions, so the ramdisk is always used. ABL concatenates vendor ramdisk + our ramdisk [V for concatenation, U for "ABL never injects skip_initramfs"] |
| `fastboot boot` | works | **works**, but the image needs an **AVB footer** (unsigned hash footer padded to 96 MiB) [S] |
| vendor/system | real partitions | inside **super** (dm-linear logical partitions, Virtual A/B) [V] |
| Kernel | 4.4, mostly built-in | 4.19 "redbull". **Highly modular**: UFS, clocks, pinctrl, DWC3 USB and DRM are all `=m` [V] |
| Rootfs | userdata | userdata (`sda19`, about 110 GiB) works the same way [V] |

---

## 1. Bootloader unlock, caveats, return to stock

**Procedure** [V]:
1. Developer options: enable **OEM unlocking** and USB debugging. The phone may need internet once for the toggle to become available ([AOSP "Flash devices"](https://source.android.com/docs/setup/test/running), [CalyxOS Verizon note](https://calyxos.org/install/verizon/)).
2. Hold Vol-Down and power on (or `adb reboot bootloader`), then run `fastboot flashing unlock` and confirm on the device. LineageOS uses exactly this as `custom_unlock_cmd` ([lineage_wiki redfin.yml](https://github.com/LineageOS/lineage_wiki/blob/master/_data/devices/redfin.yml)).
3. **Unlocking wipes userdata**. All lock-state transitions wipe data ([AVB device state](https://source.android.com/docs/security/features/verifiedboot/device-state)).

**`flashing unlock_critical`**: AOSP documents it as needed on "Pixel 2 XL only" ([source](https://source.android.com/docs/setup/test/running)). On redfin, `flashing unlock` is sufficient; the factory `flash-all.sh` flashes the bootloader and radio without it [V for the docs statement, S for redfin practice].

**Carrier variants**: **Verizon-sold Pixels cannot be bootloader-unlocked**, and the OEM-unlocking toggle stays greyed out ([CalyxOS](https://calyxos.org/install/verizon/), [Verizon community](https://community.verizon.com/discussion/1170954/google-pixel-oem-unlock)). Carrier (SIM) unlocking does not change this. Buy an unlocked/Google Store unit and check the toggle before purchase if possible.

**Anti-rollback**: Google's factory-image page (checked 2026-11) carries anti-rollback warnings only for the Pixel 6/8 series (May 2025) and the Pixel 10 series (May 2026), and **none for redfin** [V, page text]. AVB rollback indexes for boot and vbmeta_system are set to the security-patch timestamp ([BoardConfig-common.mk](https://android.googlesource.com/device/google/redbull/+/refs/heads/main/BoardConfig-common.mk)). When the device is unlocked, libavb tolerates rollback-index errors. They only matter if you relock with an older image [U for redfin specifics]. The final build is the newest anyway, so there is nothing to downgrade to.

**Back to stock**: flash the final factory image with `flash-all.sh` or [flash.android.com](https://flash.android.com), which wipes data. Relock **only after** a fully stock image boots. Relocking with any modified boot, vendor_boot, dtbo or vbmeta leaves the phone unbootable. Recovery from that state then depends on the OEM-unlocking flag still being set ([factory images page](https://developers.google.com/android/images), [ios-redfin AGENTS.md](https://github.com/maxexcloo/ios-redfin) warns "Never relock until an unmodified stock system boots") [S].

## 2. Final firmware, partition layout

### Final factory image
- **Android 14, `UP1A.231105.001.B2`, released Feb 2024**, still with the **2023-11-05** security patch. It was a surprise bug-fix build after EOL in Oct/Nov 2023 ([Droid-Life](https://www.droid-life.com/2024/02/06/pixel-5-and-pixel-4a-5g-get-surprise-update-for-february/), [Notebookcheck](https://www.notebookcheck.net/Google-pushes-new-updates-to-older-Pixel-smartphones-with-undisclosed-improvements.801582.0.html)). The LineageOS tree pins `BOOT_SECURITY_PATCH := 2023-11-05` ([LineageOS BoardConfigLineage.mk](https://github.com/LineageOS/android_device_google_redfin/blob/lineage-24.0/BoardConfigLineage.mk)) [S/V].
- **Not verified**: I could not read the redfin rows of developers.google.com/android/images, because that content sits behind the ToS click-through and the fetch did not return it. **Confirm the exact zip name and SHA-256 there.** Fingerprint of the previous build: `google/redfin/redfin:14/UP1A.231105.001/10817346`, kernel `4.19.278-g7b0944645172-ab10812814`, header v3 ([radito/kernel-msm baseline](https://github.com/radito/kernel-msm/releases/tag/baseline)) [S].

### Boot images (from [device/google/redbull BoardConfig-common.mk](https://android.googlesource.com/device/google/redbull/+/refs/heads/main/BoardConfig-common.mk)) [V]
- `BOARD_BOOT_HEADER_VERSION := 3`, `BOARD_KERNEL_PAGESIZE := 4096`, `BOARD_KERNEL_BASE := 0x00000000`. The kernel is `Image.lz4` and the ramdisk is LZ4 (`BOARD_RAMDISK_USE_LZ4 := true`).
- `boot` and `vendor_boot` are **0x06000000 (96 MiB)** each. `dtbo` is **16 MiB**.
- **vendor_boot exists** (A/B). It carries the vendor ramdisk (first-stage fstab, early kernel modules, recovery resources via `BOARD_MOVE_RECOVERY_RESOURCES_TO_VENDOR_BOOT`) and the **DTB**: `BOARD_INCLUDE_DTB_IN_BOOTIMG := true`, which with v3 places it in vendor_boot ([AOSP boot header doc](https://source.android.com/docs/core/architecture/bootloader/boot-image-header): "The DTB is stored in the vendor boot partition"). No separate recovery partition exists; LineageOS calls `vendor_boot` the "recovery" partition ([redfin.yml](https://github.com/LineageOS/lineage_wiki/blob/master/_data/devices/redfin.yml)).
- **dtbo** partition (A/B) holds the board overlays.
- Stock BOARD_KERNEL_CMDLINE, which goes into the vendor_boot cmdline: `console=ttyMSM0,115200n8 androidboot.console=ttyMSM0 printk.devkmsg=on msm_rtb.filter=0x237 ehci-hcd.park=3 service_locator.enable=1 androidboot.memcg=1 cgroup.memory=nokmem lpm_levels.sleep_disabled=1 usbcore.autosuspend=7 androidboot.usbcontroller=a600000.dwc3 swiotlb=2048 androidboot.boot_devices=soc/1d84000.ufshc loop.max_part=7 ... cgroup_disable=pressure`. **No `root=` is set.**
- AB_OTA_PARTITIONS: boot, vendor_boot, dtbo, vbmeta, vbmeta_system, system, system_ext, product, vendor, plus firmware.

### Dynamic partitions / super [V]
- `super` = **9 755 951 104 bytes**, with group `google_dynamic_partitions` of 6 GiB - 4 MiB. It contains `system`, `system_ext`, `product` and `vendor` ([BoardConfig](https://android.googlesource.com/device/google/redbull/+/refs/heads/main/BoardConfig-common.mk), [fstab.hardware](https://github.com/LineageOS/android_device_google_redbull/blob/lineage-24.0/fstab.hardware)).
- **Virtual A/B**: `device-redfin.mk` inherits `virtual_ab_ota/launch_with_vendor_ramdisk.mk` ([LineageOS device-redfin.mk](https://github.com/LineageOS/android_device_google_redfin/blob/lineage-24.0/device-redfin.mk)). Normally only the current slot's logical partitions exist. Snapshot state lives in `/metadata` (sda15).
- **Implication for Linux**: to reach vendor firmware (`/vendor/firmware/*`), parse the super metadata and build dm-linear mappings. Options are [parse-android-dynparts](https://github.com/tchebb/parse-android-dynparts) piped to `dmsetup create`, or `lpunpack` from android-tools. Do this **once**, copy the blobs into the rootfs (`/lib/firmware/...`), and leave super untouched afterwards. Do this after a clean factory flash, when no OTA snapshot merge is pending. The kernel needs `CONFIG_BLK_DEV_DM=y`, which is set.

### Firmware locations (important for modem, DSP, WLAN, BT and GPU)
- **No separate `dsp` or `bluetooth` partitions** exist on redfin, unlike Pixel 2/3 [V, by-name dump below].
- `modem_a/_b` (sda12/13) is **vfat, mounted read-only at `/vendor/firmware_mnt`**. ueventd's `firmware_directories` is `/vendor/firmware_mnt/image/` ([fstab.hardware](https://github.com/LineageOS/android_device_google_redbull/blob/lineage-24.0/fstab.hardware), [ueventd.rc](https://github.com/LineageOS/android_device_google_redbull/blob/lineage-24.0/ueventd.rc)). It holds the modem (MPSS) images and possibly others.
- `/vendor/firmware/` (inside super/vendor) holds `adsp.*`, `cdsp.*`, GPU `a620_zap.*` / `a650_sqe.fw` / `a619_gmu.bin`, WLAN board data `bdwlan-redfin.bin`, BT `crbtfw32.tlv` / `crnv32*.bin`, `ipa_fws.*`, and others ([proprietary-files-vendor.txt](https://github.com/LineageOS/android_device_google_redfin/blob/lineage-24.0/redfin/proprietary-files-vendor.txt)).
- `persist` (sda2, ext4, 32 MiB) holds sensor registry/calibration, rfs, WLAN/BT data and more ([fstab.persist](https://github.com/LineageOS/android_device_google_redbull/blob/lineage-24.0/fstab.persist), [init.hardware.rc](https://github.com/LineageOS/android_device_google_redbull/blob/lineage-24.0/init.hardware.rc)).
- `modemst1`/`modemst2`/`fsg`/`fsc` (sdf2-5) hold modem EFS (IMEI, RF calibration). **Back these up before anything else, along with persist.**
- Bootloader-side firmware, which LineageOS ships from the factory image and which **we never touch**: abl, aop, devcfg, featenabler, hyp, keymaster, modem, qupfw, tz, uefisecapp, xbl, xbl_config ([proprietary-firmware.txt](https://github.com/LineageOS/android_device_google_redfin/blob/lineage-24.0/redfin/proprietary-firmware.txt)).

### UFS layout (`ls -l /dev/block/by-name`, Android 13 TP1A.220624.014 dump, [newandroidbook ddb Pixel5](https://newandroidbook.com/ddb/Pixel5/)) [V]
- **sda (LUN0)**: ssd=1, **persist=2**, misc=3, keystore=4, frp=5, **boot_a/b=6/7, vendor_boot_a/b=8/9, dtbo_a/b=10/11, modem_a/b=12/13**, klog=14, **metadata=15, vbmeta_system_a/b=16/17, super=18, userdata=19**
- **sdb / sdc (boot LUNs)**: xbl_a, xbl_config_a / xbl_b, xbl_config_b
- **sdd**: ALIGN_TO_128K_1, cdt, ddr
- **sde**: aop 1/17, tz 2/18, hyp 3/19, abl 4/20, keymaster 5/21, cmnlib 6/22, cmnlib64 7/23, devcfg 8/24, qupfw 9/25, **vbmeta_a/b 10/26**, reserve 11/27, uefisecapp 12/28, imagefv 13/29, apdp 14/30, multiimgoem 15/31, featenabler 16/32, devinfo 33, spunvm 34, splash 35, limits 36, limits-cdsp 37, toolsfv 38, logfs 39, storsec 40, uefivarstore 41, secdata 42
- **sdf**: ALIGN_TO_128K_2, modemst1=2, modemst2=3, fsg=4, fsc=5
- **userdata size**: `/data` showed 114 407 404 1K blocks, about **109 GiB** on the 128 GB model. The 10 GiB `BOARD_USERDATAIMAGE_PARTITION_SIZE` is only the build-image size.
- Under Linux, **refer to partitions by PARTLABEL** (`/dev/disk/by-partlabel/userdata`), not by `sdX`. LUN enumeration order is not guaranteed, especially with async probe or a mainline kernel. The UFS controller is at `1d84000.ufshc`.

## 3. `fastboot boot` on redfin
- **Works with an unlocked bootloader.** TWRP's official install method for redfin is `fastboot boot path/to/twrp.img` ([TWRP Pixel 5 page](https://github.com/TeamWin/twrpme/blob/master/_google/googlepixel5.markdown)). The ios-redfin project boots its shim with `fastboot boot` ([ios-redfin](https://github.com/maxexcloo/ios-redfin)), and the radito kernel project says to "test with `fastboot boot` before flashing" ([radito](https://github.com/radito/kernel-msm/releases/tag/baseline)). Petr Vorel tested U-Boot chainloading via fastboot on Pixel 5 ([u-boot list, Jan 2026](https://lists.denx.de/pipermail/u-boot/2026-January/607176.html)) [S, multiple].
- **Quirks for header v3**:
  - **An AVB footer is required even when unlocked.** Without it, ABL fails with *"Error verifying the received boot.img: Unsupported"*. The fix is `avbtool add_hash_footer --image boot.img --partition_size 100663296 --partition_name boot` (unsigned, padded to 96 MiB). Source: ios-redfin `shim/build.sh` [S, single source but concrete].
  - **Only boot.img is sent.** ABL still uses the **active slot's flashed vendor_boot** (DTB, vendor ramdisk, vendor cmdline) and **dtbo**. A custom DTB or vendor cmdline therefore requires flashing vendor_boot (and possibly dtbo), ideally on the *other* slot. Our ramdisk is appended *after* the stock vendor ramdisk ([vendor_boot doc](https://source.android.com/docs/core/architecture/partitions/vendor-boot-partitions): "must load the generic ramdisk into memory immediately following the vendor ramdisk"). The stock vendor ramdisk's `/lib/modules/*.ko` and `first_stage_ramdisk/` files end up in our initramfs too: harmless, but they cost RAM, and same-path files are overwritten by ours. Make sure our `/init` exists.
  - **Kernel text offset must be 0x80000.** *"Snapdragon Google Pixel bootloaders require the TEXT_OFFSET to be exactly 0x80000. Without this, U-Boot or kernels will fail to load"* ([u-boot patch](https://go.mail-archive.com/u-boot@lists.denx.de/msg562872.html)). The downstream 4.19 kernel satisfies this. Mainline arm64 Images have had text_offset 0 since v5.8, so **mainline may need a header patch or a U-Boot chainload** [S, flag for the mainline agent].
  - mkbootimg invocation used by others: `mkbootimg --header_version 3 --kernel Image.lz4 --ramdisk initrd.lz4 --os_version 14.0.0 --os_patch_level 2023-11 --cmdline "..."`. With v3 there are no load-address arguments in boot.img; those come from vendor_boot.

## 4. Kernel cmdline and DTB selection
- **Final cmdline** = vendor_boot cmdline (stock string above) + boot.img cmdline + ABL-injected `androidboot.*` parameters (serialno, slot_suffix, verifiedbootstate, vbmeta digest, bootreason, and similar) [V for the first two parts, U for the exact ABL list]. Kernel 4.19 with header v3 does **not** use bootconfig, which needs header v4 and kernel 5.10 or later, so everything appears in `/proc/cmdline`.
- **`skip_initramfs`**: not expected. Devices launching with Android 10 or later use first-stage init in the ramdisk, and Android 10+ "must use a ramdisk" ([system-as-root doc](https://source.android.com/docs/core/architecture/partitions/system-as-root)). Recovery resources live in vendor_boot, so ABL distinguishes normal boot from recovery with **`androidboot.force_normal_boot=1`** ([ramdisk partitions doc](https://source.android.com/docs/core/architecture/partitions/ramdisk-partitions)). The redbull kernel *still contains* `skip_initramfs` handling in `init/initramfs.c` ([LineageOS kernel](https://github.com/LineageOS/android_kernel_google_redbull/blob/lineage-24.0/init/initramfs.c)), so if ABL ever passed it, the initramfs would be dropped. **Unverified**: dump `/proc/cmdline` from a first test initramfs. The `skip_initramfs` patch from the Pixel 2 project is probably unnecessary, and keeping it would be harmless.
- **`root=`**: not injected by the build config. Our initramfs mounts the rootfs itself, e.g. `root=PARTLABEL=userdata`, handled by our init.
- **DTB/DTBO selection** [V for IDs, U for ABL failure behaviour]: vendor_boot contains base SoC DTBs (`qcom-base/lito.dtb` and `lito-v2.dtb`). ABL picks one by `qcom,msm-id` / `qcom,board-id`, then applies the matching overlay from `dtbo`. The redfin PVT overlay declares:
  ```
  model = "Google Inc. MSM sm7250 v2 Redfin PVT";
  compatible = "google,redfin-sm7250", "qcom,sm7250";
  qcom,msm-id = <400 0x20000>, <440 0x20000>;
  qcom,board-id = <0x0b1e05 0>;
  ```
  ([lito-v2-redfin-pvt-overlay.dts](https://github.com/LineageOS/android_kernel_google_redbull/blob/lineage-24.0/arch/arm64/boot/dts/google/lito-v2-redfin-pvt-overlay.dts), [dts Makefile](https://github.com/LineageOS/android_kernel_google_redbull/blob/lineage-24.0/arch/arm64/boot/dts/google/Makefile))
- **Mainline DTB**: with v3 there is no DTB in boot.img. The mainline DTB must go into **vendor_boot's DTB section** (`mkbootimg --vendor_boot ... --dtb`) and carry matching `qcom,msm-id`/`qcom,board-id`. ABL will also try to apply the stock dtbo overlay to it, so flash an empty or matching dtbo, or erase dtbo, on the Linux slot. Whether ABL treats an overlay-apply failure as fatal is **untested**. `CONFIG_BUILD_ARM64_APPENDED_DTB_IMAGE=y` is in the defconfig, but nothing shows ABL honouring an appended DTB with v3 (ios-redfin says ABL "takes the DTB from vendor_boot") [S]. An alternative that sidesteps ABL's DTB handling is to `fastboot boot` **U-Boot** (now upstream: `qcom_defconfig google-pixel.config qcom-phone.config`, tested on Pixel 5) and let U-Boot load kernel and DTB ([u-boot google-pixel.config](https://elixir.u-boot.org/u-boot/master/source/board/qualcomm/google-pixel.config)). Mainline redfin DTS did not exist as of Jan 2026 ("Pixel 5 has for now no mainline Linux support (missing device-tree)", David Heidelberg).

## 5. AVB
- Chain: `vbmeta` (sde10/26) → `boot` (hash, rollback location 2), `vendor_boot`, `dtbo`, `vendor` (hashtree) and the chained **`vbmeta_system`** (sda16/17, covering system, system_ext and product; rollback location 1) [V, BoardConfig].
- To disable: `fastboot flash vbmeta --disable-verity --disable-verification vbmeta.img`, using the stock `vbmeta.img` from the factory zip, per slot or with `--slot=all`. Setting `AVB_VBMETA_IMAGE_FLAGS_VERIFICATION_DISABLED` on the top-level vbmeta means *"verification will be disabled and descriptors will not be parsed"* ([avb_vbmeta_image.h](https://android.googlesource.com/platform/external/avb/+/refs/heads/main/libavb/avb_vbmeta_image.h)). Chained `vbmeta_system` is therefore not checked and **does not need to be modified** [V for semantics, U that ABL behaves exactly per libavb].
- **Consequences**: orange/"can't be verified" boot warning on every boot (already present when unlocked). Changing the vbmeta flags on a phone with existing Android data reportedly requires **a userdata wipe** before Android boots again, because forum reports describe bootloops until a wipe [S]. That is irrelevant here, since userdata becomes the Linux rootfs. Even with verification disabled, ABL still wants the AVB footer on images sent via `fastboot boot` (see §3).

## 6. Downstream kernel
- **AOSP branches** (kernel/msm): `android-msm-redbull-4.19-android14-qpr3` is the last QPR. It is at 4.19.**294** and was last touched around mid-2024. Also present: `android-msm-redbull-4.19-android14-release`, `-android14-qpr1/2`, `-android13*`, and others ([refs](https://android.googlesource.com/kernel/msm/+refs), [log](https://android.googlesource.com/kernel/msm/+log/refs/heads/android-msm-redbull-4.19-android14-qpr3), [Makefile](https://android.googlesource.com/kernel/msm/+/refs/heads/android-msm-redbull-4.19-android14-qpr3/Makefile)). No `redbull` tags were found. Build with repo manifest `kernel/manifest` branch `android-msm-redbull-4.19-android14-qpr3`, which pulls msm-google plus techpacks (audio, camera, display, video, dataipa) and out-of-tree qcacld-3.0 WLAN and fts/sec touch. Run `build/build.sh` with `build.config.redbull.no-cfi` ([manifest](https://android.googlesource.com/kernel/manifest/+/refs/heads/android-msm-redbull-4.19-android14-qpr3/default.xml)). The pinned toolchain is **clang-r416183b** (Clang 12), with `LLVM=1` ([build.config.common](https://android.googlesource.com/kernel/msm/+/refs/heads/android-msm-redbull-4.19-android14-qpr3/build.config.common)).
- **Better fallback: LineageOS `android_kernel_google_redbull`, branch `lineage-24.0`.** It is actively maintained (**commits on 2026-11-07**) and merged to **4.19.325**, the final 4.19 LTS ([repo](https://github.com/LineageOS/android_kernel_google_redbull)). Lineage builds it with its default AOSP clang (`TARGET_KERNEL_CLANG_VERSION` unset → `LLVM_AOSP_PREBUILTS_VERSION`, [BoardConfigKernel.mk](https://github.com/LineageOS/android_vendor_lineage/blob/lineage-24.0/config/BoardConfigKernel.mk)), so **it builds with modern clang** [V that it is unpinned, U for the exact version, probably clang 19 or 20]. Defconfig is `redbull_defconfig` (Lineage `TARGET_KERNEL_CONFIG`).
- **Config notes for systemd / Ubuntu 24.04** (systemd 255 needs kernel ≥3.15 and DEVTMPFS, CGROUPS, INOTIFY_USER, SIGNALFD, TIMERFD, EPOLL, UNIX, SYSFS, PROC_FS, FHANDLE per the [systemd v255 README](https://raw.githubusercontent.com/systemd/systemd/v255/README)). From [redbull_defconfig](https://github.com/LineageOS/android_kernel_google_redbull/blob/lineage-24.0/arch/arm64/configs/redbull_defconfig):
  - **Missing, must add**: `CONFIG_DEVTMPFS(+_MOUNT)`, `CONFIG_FHANDLE` (explicitly not set), `CONFIG_AUTOFS4_FS`. Recommended: `CONFIG_PID_NS` (not set), `CONFIG_USER_NS`, `CONFIG_VT` + `CONFIG_FRAMEBUFFER_CONSOLE` if a text console is wanted (VT is not set).
  - **Remove or change**: `CONFIG_STATIC_USERMODEHELPER=y` with an empty path, which disables *all* usermode helpers (modprobe autoload, coredump pipes). `CONFIG_FW_LOADER_USER_HELPER(_FALLBACK)=y`, because systemd-udev no longer serves firmware requests and every missing firmware would stall about 60 s; disable it, or pass `firmware_class.path=`. Consider dropping `CONFIG_LTO_CLANG`/`CONFIG_CFI_CLANG` (AOSP's no-cfi config already switches to ThinLTO without CFI) for faster, safer builds. SELinux is on: boot `selinux=0` or set it permissive.
  - **`CONFIG_ANDROID_PARANOID_NETWORK` does not exist in this tree** (absent from `net/Kconfig`), so no AID_INET socket restrictions apply [V].
  - Present and helpful: CGROUPS/MEMCG/BPF/CGROUP_BPF, PSI, SECCOMP, NAMESPACES, IKCONFIG, BINDERFS, EXT4/F2FS/VFAT, BLK_DEV_DM, USB_CONFIGFS (NCM, mass storage, FFS), EVDEV.
- **Modularity is the big difference from the Pixel 2/4.4 kernel.** Defconfig has `SCSI_UFSHCD/UFS_QCOM=m`, `PINCTRL_LITO=m`, `SM_GCC_LITO` and all clock controllers `=m`, `USB_DWC3(_MSM)=m`, `SERIAL_MSM_GENI=m`, `DRM_MSM=m` (downstream SDE), `QCOM_KGSL=m`, `QRTR`, `RPMSG_GLINK`, `MSM_PIL`/SSR `=m`, and so on. **The initramfs must carry and load these in order** (use `modules.load` from [device/google/redbull](https://github.com/LineageOS/android_device_google_redbull/blob/lineage-24.0/modules.load)) before UFS or USB gadget networking is available. Alternatively, flip the essentials to `=y` [U whether all of them build as built-ins]. Modules must come from the *same* build, with MODVERSIONS on; stock `.ko` files will not load into a custom kernel ([android-building thread](https://groups.google.com/g/Android-building/c/p8jPr_S9PRc)).
- **Is it a realistic fallback like 4.4 was on walleye?** **Yes, for bring-up**: maintained source, a known-good boot path, and every peripheral driver exists. It is harder than 4.4 because of the module dependency chain, the downstream display stack (SDE DRM rather than upstream DPU; KGSL GPU, not msm DRM, so GL needs Mesa's KGSL backend via turnip/zink or software rendering [U]), and the Android-specific firmware paths.

## 7. Risks: what can wipe or brick
1. **Hard-brick class (avoid)**: flashing xbl/xbl_config/abl/tz/hyp/aop/devcfg/keymaster/etc. (sdb/sdc/sde) with anything but matching Google images. **Relocking** with non-stock images. Never write `sdb`/`sdc`/`sde` from Linux. Never write raw `sdX` names, use partlabels.
2. **Data/identity loss**: `persist`, `modemst1/2`, `fsg` and `fsc` are device-unique (IMEI/EFS, Wi-Fi/BT/sensor calibration). **Back them up with `dd`** from the first test initramfs (Android root is not available without Magisk). Do not let Linux userspace mount `persist` read-write casually.
3. **Wipes**: unlocking and relocking wipe userdata. `flash-all.sh` and `fastboot -w` wipe userdata (that is, the Ubuntu rootfs). If Android boots on the other slot and cannot mount `/data` (f2fs plus FBE plus metadata encryption keyed in `/metadata`, fstab flag `formattable`), it lands in recovery with "Cannot load Android system… Factory data reset", and **choosing reset destroys the rootfs**. Android also writes `/metadata`. Do not dual-boot Android against a Linux userdata, or put the rootfs elsewhere/as an image [U for the exact fs_mgr behaviour on ext4-formatted userdata].
4. **Slot pitfalls**: boot, vendor_boot, dtbo, vbmeta and modem are A/B (physical). `fastboot flash X` writes the *current* slot. Use explicit `X_a`/`X_b` or `--slot`. If the Linux slot is never marked successful, ABL decrements the retry counter and eventually falls back or marks the slot unbootable. Use [qbootctl](https://github.com/linux-msm/qbootctl) from Linux to mark boot successful (redfin uses QTI GPT-attribute boot control: `android.hardware.boot-service.qti` in LineageOS) [U that qbootctl is redfin-compatible]. Logical partitions (super) exist for **one slot only** (Virtual A/B), so "Linux on slot B, Android on slot A" works only for the physical boot partitions.
5. **Recoverability**: ABL/fastboot (Vol-Down + Power) survives any boot/vendor_boot/dtbo/vbmeta/userdata mistake, and the factory image restores everything. Recommended workflow: tethered `fastboot boot` first, and flash vendor_boot/dtbo only to the non-Android slot.
6. **Anti-rollback**: no Google-documented ARB fuse for redfin (§1). The final build is the newest, so a stock re-flash never downgrades.
